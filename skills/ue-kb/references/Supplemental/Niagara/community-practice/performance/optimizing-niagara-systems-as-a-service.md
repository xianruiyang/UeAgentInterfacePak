## 概述

在 5.4 版本之前，用于生成 Niagara 系统的 API 主要支持系统实例与游戏事件/外部触发器之间的一对一关系。Niagara 系统几乎不允许外部代码传递粒子生成时间和初始化方式的信息，而只能通过激活和移动组件来实现。如果需要在短时间内生成同一系统的多个实例，就会出现问题，因为激活成本和实例数量都可能导致严重的性能问题。从概念上讲，系统即服务 (SaaS) 采用的是外部触发器和系统实例之间的多对一模式。也就是说，一个系统实例可以处理来自多个触发器的粒子生成，而无需重新激活，从而避免了激活和运行多个实例所带来的成本。

用户参数和数组数据接口使得高级用户可以将粒子“注入”到现有系统中，但这种工作流程存在局限性，并且在构建数组时需要大量的手动数据管理。此外，基于数组的方法需要手动管理实例剔除，而实例剔除又与 SaaS 系统实例的大小之间存在权衡。举个极端的例子，如果项目中的所有粒子特效都在同一个系统中，大多数情况下，屏幕外的粒子数量将远远超过屏幕上的粒子数量，但由于系统本身始终处于活动状态，它们的模拟仍然会运行。

为了更全面地解决这个问题，并简化设置，我们开发了 Niagara 数据通道，它提供了一种在 Niagara 系统和游戏之间传递数据的通用方式。我们主要关注的是 SaaS 用例，但数据通道还有其他用例，这里就不一一赘述了。我们创建了一种特殊的数据通道类型——岛屿数据通道，它负责细分关卡，并在这些“岛屿”中生成系统实例，用于存储写入其边界内的数据。数据通道资源定义了它将包含的数据以及它将生成的系统，并在数据写入时自动处理所有操作。

本指南将介绍两种方法，旨在提供更多选择并进行比较，同时展示升级路径。Lyra 项目在之前的版本中使用了基于数组的生成机制，而在 5.4 版本中，我们更新了其冲击效果机制以支持使用 Niagara 数据通道，因此我们将以 Lyra 作为两种方法的示例。

当发送有效载荷数据时，无论是使用数组还是数据通道，一般流程是：写入数据（通常来自游戏代码），根据该数据在 Niagara 系统中生成粒子，然后读取该数据以初始化粒子。 User Parameter SaaS 用户参数 SaaS

“冲击生成属性”模块稍微复杂一些。它使用粒子的执行索引、起始偏移量和命中次数来索引提供的数组。最初使用起始偏移量是因为所有冲击表面类型的数据都被打包到同一个数组中。起始偏移量是特定表面数据开始的索引，因此每个系统都会从与其表面类型对应的偏移量开始读取数据。命中次数用作模数，以便在粒子数量多于冲击位置时循环粒子。然后，该模块使用这些数据来计算模拟中其他地方使用的值，例如冲击法线、切线和粒子位置。

为了支持数据通道，重构过程中，用于存储这些数据的数组根据表面类型被拆分成结构体。这使得支持不同表面类型的不同生成策略变得更加容易，并且消除了对起始偏移量的需要。

这些系统采用的设置方式是循环一次，每次激活只会生成一次粒子束。这避免了数组数据可能过时的问题。可以使用“移除最后一个元素”节点从数组末尾读取并移除值来清除数据。但这种方法不适用于这些冲击系统，因为存在多个发射器，需要多次读取数据。虽然可以在外部或在粒子模拟中清除这些值，但这可能会导致竞争条件。使用新数据重新激活系统是一个可以接受的折衷方案，尽管重新激活系统会带来额外的开销。 Data Channel SaaS SaaS 渠道数据

数据通道自动处理 SaaS 方法的许多方面，包括将数据写入正确的系统、生成和放置这些系统以及系统生命周期管理。这简化了用例，并优化了其中一些步骤，从而提供比基于数组的方法更好的性能。有关 Niagara 数据通道的入门教程，请点击以下链接。简而言之：创建 Niagara 数据通道资产定义了发送到 Niagara 系统的数据结构；对于 Islands 数据通道，它还定义了要生成哪些系统，以及在向该数据通道写入数据时如何生成这些系统。然后，系统定义了生成粒子和读取数据的行为，以便在更广泛的模拟中使用。数据通道提供节点以方便条件生成，并提供生成范围以允许在不同情况下生成可变数量的粒子。

对于碰撞事件，数据通道数据用于初始化粒子，并在粒子生成脚本阶段使用 NM_ImpactReadDataChannel 模块读取一次。NM_ImpactReadDataChannel 会重新创建 NM_ImpactSpawnAttributes，只是数据源不同。它使用存储在生成模块中的数据通道接口，并以生成组作为索引来读取数据。当使用“生成条件”生成粒子时，它会将粒子的生成组设置为与其在数据通道中的数据索引相对应。读取数据时，如果读取成功，它会返回一个布尔值，模块会根据此结果选择使用默认数据或从数据通道读取的数据。 Instead of using the spawn index, we have now added Get NDCSpawn Data on the Data Channel Reader data interface,

验证性能变化以确保其符合预期至关重要。就数据通道与阵列而言，两种方法的性能应该都相当不错。数据通道在生成系统方面可能优于阵列，而阵列在模拟成本方面可能优于数据通道，因为阵列系统更为简单。然而，由于阵列方法使用了两个系统而非一个，如果两种表面类型的出现频率相近，则组合系统可能会带来更少的开销。此外，比较两种方法还有助于发现进一步的优化机会。

以下是 NS_ImpactDataChannel 的详细分析。它的平均耗时为 0.03 毫秒，低于阵列系统的平均耗时，但由于其频率分布不均，其性能与之前基本持平，甚至略有下降。这符合直觉，因为该系统拥有更多的发射器实例，并且处理多种表面类型的逻辑也更为复杂。此外，值得注意的是，两种方法中使用的系统边界特性也截然不同。

对于数组生成，距离阈值为 500 个单位，这导致实例数量更多，但每个实例覆盖的体积更小。这有利于剔除不必要的粒子，但不利于实例数量。另一方面，对于数据通道，每个轴的范围为 5000 个单位，这导致实例数量更少，但每个实例覆盖的体积更大，其结果恰恰相反，有利于减少剔除，并减少实例数量。NS_ImpactDataChannel 的部分帧开销可能（甚至很可能）来自于模拟许多屏幕外的粒子。
