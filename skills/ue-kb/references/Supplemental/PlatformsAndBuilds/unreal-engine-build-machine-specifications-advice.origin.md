### 概览

*文章由 [Branden T.](https://dev.epicgames.com/community/profile/Kzq2/Branden.Turner) 撰写* 我们有时会收到请求，不仅为虚幻开发机器推荐规格，还为自动构建节点推荐规格。这个问题的最佳答案是典型的“视情况而定”。我们将使用 AWS 实例作为讨论我们当前（截至 21 年 3 月 1 日）使用的基础，这可能超出您的项目需求。还有一些一般准则在大多数情况下都会有所帮助。首先，在选择机器时的一些一般建议：如果可能，您至少希望将代理分为编译器和炊具，因为两者可以具有不同的规格，使它们在一项任务上比另一项任务更好。 Cookers 将需要更多的 RAM 和更快的时钟速度（磁盘空间和 I/O 速度也不会受到影响），而编译器将需要更高的核心数量 Cooker 内存需求将因项目而异。例如，我们的一些较大的项目需要多达 128GB 的​​ RAM，而较小的项目则不需要那么多。对于 Cookers 来说，最好的想法是在本地分析当前的内存使用情况以进行烹饪，这将帮助您找出要使用的最佳实例类型。编译器更加简单，因为更多的内核允许同时执行更多的任务，这使得它成为一个非常有吸引力的优化属性。一些编译作业仍然会使用大量内存，因此更高的 RAM 将有助于提高稳定性。如果您的预算有限，一般建议是“购买 RAM 直到您的构建稳定，然后投资核心”。现在更具体地说：对于我们的编译器，我们发现 r5.8xlarge AWS 实例在大多数情况下都能满足我们的需求。 r5 实例类型为我们提供了核心数量的完美融合，同时仍然为我们提供了足够的内存以保证稳定性。根据项目的大小，C5 实例也可能很合适，但它们可能会出现一些虚拟内存问题。这因项目而异，因此测试会有所帮助。对于烹饪，我们使用 z1d.6xlarge 实例。 z1d 实例为我们提供了最快的核心时钟速度、良好的内存和高 I/O 能力的存储。 C5 实例没有足够的内存来满足我们的需求，但它们可以根据您的项目工作。 R5 实例没有我们需要的时钟速度。绝对在本地进行配置并查看！上述指南普遍适用，但请再次自行测试并配置不同的设置，以确保满足您的所有需求。
