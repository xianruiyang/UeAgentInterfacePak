# 设计文档规范

## 1. 目的

本文档定义中型以上白盒关卡在正式搭建前必须完成的最小设计包。

如果你是在找整体顺序，请先看：
- [whitebox-workflow.md](whitebox-workflow.md)

## 2. 适用范围

满足下列任一条件的白盒，正式搭建前必须先完成最小设计包：
- 多层结构明显
- 目标时长大于 20 分钟
- 存在锁钥链
- 使用多类设施
- 存在明显跑酷链或复杂跨楼层连接
- 存在成组收集品分布

## 3. 设计包定位

### 3.1 设计包是施工前置物

设计包不是事后归档附件，也不是脚本说明的替代品。

没有设计包，中型以上白盒不得正式开搭。

### 3.2 设计包是结构真源的上游

设计包先定义：
- 关卡是什么
- 当前白盒承载什么玩法
- 玩家能做什么
- 空间怎么组织
- 空间之间怎么连接
- 设施服务什么路径
- 什么叫验收通过

之后结构表、生成脚本和白盒几何都应从这里继续细化。

## 4. 最小设计包

### 4.1 玩家能力模型

必须先锁玩家能力模型。至少写清：
- 胶囊体尺寸
- 基础移动方式
- 跳跃能力
- `step height`
- 交互方式
- 死亡与复活规则（跌落虚空、检查点/篝火）
- 关键限制
- 任何直接影响空间尺寸与可达判断的特殊能力

同时必须锁一份“指标表”（Metrics），用于让尺寸口径在全关卡内可复用、可生成、可验收。至少写清：
- 门净宽、走廊净宽、楼梯净宽（默认值 + 例外规则）
- 最小净高与最小落脚区（用于判定“空间是否成立/是否可达”）
- 常用交互距离（用于放置终端、按钮、收集品等）

没有这部分，就不能对“可达”“连通”“跑酷成立”下结论。

### 4.2 关卡类型定义

关卡类型定义不得把不同维度的词混成一个标签。至少拆成：
- 结构形态
- 组织方式
- 玩家一眼看上去应识别成什么
- 它不是什么

示例：
- 结构形态：高塔
- 组织方式：局部箱庭 / 回环探索
- 玩家识别目标：一座围绕塔芯持续向上推进的塔
- 不是什么：横向铺开的多层测试场、单走廊线性关卡

说明：
- `高塔` 属于结构形态
- `箱庭`、`线性`、`hub-and-spoke` 属于组织方式
- 两者不能再写成同一层级的并列概念

### 4.3 当前白盒承载的玩法列表

必须逐项列出当前白盒实际承载的玩法，而不是只写一句抽象口号。每项至少写清：
- 玩法名称
- 它是主路径玩法、支路玩法还是辅助玩法
- 它通过哪些空间和连接承载
- 设施和收集品在其中承担什么作用
- 玩家重复执行的动作链是什么

说明：
- 锁钥不是玩法类型，而是组织可达关系、节奏和路径变化的设计工具
- 锁钥应写进设施使用契约、连接表和验收标准，而不应单独占一个“玩法列表”项

### 4.4 空间清单与主结构骨架

必须先列出空间清单，再写主结构。每个空间至少写清：
- 空间名称
- 所属层级
- 空间职责
- 该空间承载的主要玩法

在空间清单基础上，再写：
- 主路径
- 支路
- 回环
- 关键节点
- 高差组织方式
- 主要视线与回望关系

### 4.5 空间形状、尺寸与原点约定

每个空间必须写清：
- 空间原点如何定义
- 主要形状
- 长宽高或关键尺寸
- 可站立面的有效范围
- 是否有开洞、外挑、缺口、洞边或平台边

如果空间不是规则长方体，也至少要把主要轮廓拆成若干可解释子区域，而不是只写抽象名称。

### 4.6 空间连接表

至少写清：
- 哪些空间需要连接
- 连接属于主路径、支路还是回环
- 连接为什么存在
- 哪些连接跨楼层
- 是否允许跨非相邻层

这里先按空间拓扑写，不先绑定具体设施类型。

### 4.7 出入口表

每个空间的每个出入口都必须单独列出，至少写清：
- 出入口名称
- 所属空间
- 对接到哪个空间或连接单元
- 出入口尺寸
- 出入口位置
- 出入口朝向

其中“出入口位置”必须按相对于该空间自身原点的口径记录，不能只写世界坐标。

### 4.8 竖向连接单元表

每条竖向连接必须先按“跨楼层连接单元”记录，而不是先写设施名。至少写清：
- `upper_use_zone`
- `lower_use_zone`
- `approach_side`
- `exit_side`
- `landing_surface_upper`
- `landing_surface_lower`
- `required_clearance`

中型以上白盒还必须补齐可执行契约字段：
- `upper_walkable_area`
- `lower_walkable_area`
- `approach_corridor`
- `exit_corridor`
- `required_opening`
- `forbidden_blocking_volume`
- `support_pattern`
- `must_pass_width`
- `must_pass_height`

说明：
- 这些字段不是“补充说明”，而是生成器和验收能落地的最小约束
- 没有这组字段，楼梯、电梯、斜坡、`Zipline` 都不该开始摆

### 4.9 设施使用契约

至少写清：
- 门、电梯、`Zipline`、控制终端各自服务哪条路径
- 它们属于主路径还是支路设施
- 它们参与哪段锁钥链
- 它们启用前后如何改变可达图

### 4.10 收集品与可选内容分布

至少写清：
- 每组收集品的分布意图
- 它们属于主路还是支路
- 奖励、引导或节奏作用是什么

中型以上自动化白盒还应补齐“可执行口径”，否则很容易出现“看得见但吃不到 / 悬空 / 掉进洞里”的失败：
- 每组收集品绑定的 `walkable_area / landing_surface`（它属于哪块可行走完成面）
- 相对该区域的偏移与离地高度范围（例如常用 `+40~60cm`）
- 该点位的接近方式与触发可达（能站到、能靠近、能触发）

### 4.11 验收标准

至少写清：
- 关卡类型如何判定成立
- 当前玩法列表如何判定成立
- 空间连接如何判定成立
- 跨楼层连接如何判定成立
- 关键设施如何判定可用
- 哪些情况算失败并应返工

中型以上白盒还必须补一条：逐条竖向连接验收。每条楼梯、电梯、斜坡、`Zipline` 都必须单独回答：
- 从上端能否接近并进入
- 使用后能否稳定到达下端
- 到达后能否离开并继续推进
- 过程是否存在阻挡体积、缺口、悬空落点或不可解释缝隙

第一次自动化生成时，验收标准必须覆盖“第一次必过清单”的结构项（门/楼梯/电梯/Zipline/收集品等）。建议把它作为验收清单引用：
- [../checklists/first-automation-generation-checklist.md](../checklists/first-automation-generation-checklist.md)

## 5. 推荐顺序

1. 先锁玩家能力模型
2. 写关卡类型定义
3. 写当前白盒承载的玩法列表
4. 列空间清单与主结构骨架
5. 写每个空间的形状、尺寸和原点约定
6. 写空间连接表
7. 写每个空间的出入口表
8. 写竖向连接单元表
9. 写设施使用契约
10. 写收集品/可选内容分布
11. 写验收标准
12. 再开始结构表和几何生成

## 6. 禁止做法

- 没有设计包就直接开始搭中型以上白盒
- 只有生成脚本，没有设计包
- 只有截图，没有结构约束和验收标准
- 设计包写成场景完成后的事后总结
- 只写空间名称，不写空间尺寸、形状和原点
- 只写“有一个门/出口”，不写每个出入口相对空间原点的位置与尺寸
- 只写“有楼梯/电梯/Zipline”，不写竖向连接单元的可执行契约
- 只做整体截图验收，不做逐条竖向连接验收
