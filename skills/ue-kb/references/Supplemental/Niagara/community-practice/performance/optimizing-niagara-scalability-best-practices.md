## 优化尼亚加拉瀑布 | 可扩展性和最佳实践

## 概述

本文档概述的策略的主要目标是减少粒子系统在个体和整体层面上所做的工作量。第一个教程中的指导将帮助您找到额外工作所在，而本教程将为您提供修改这些方面的工具和选项。在减少总体工作量时，我们可以避免不必要的工作，或者选择开销更小的解决方案。

## 实例计数：减少该级别的系统数量

即使是经过优化的系统，如果关卡中系统数量过多，也会冲击效果性能。默认情况下，我们使用 Niagara 世界管理器分批运行同一系统的实例，但系统实例越多，游戏线程需要处理的工作就越多。一般来说，在更多实例上模拟相同数量的粒子会降低性能，因为计算量更大，但更多实例可以让 Niagara 更精细地剔除粒子，因此需要在少量大规模实例和大量小规模实例之间进行权衡。

## 实例数量减少策略

总的来说，你可以通过控制关卡中生成的系统数量，或者在系统生成后更积极地剔除它们来减少实例数量。两种方法各有优势，我们也提供了相应的工具，但通常最好先为你的项目设置一些核心效果类型，并确保所有 Niagara 系统都分配了相应的效果类型。

## 可扩展性和效应类型

提供了多种可扩展性选项，包括可重用的资源，这些资源可以通过我们的“效果类型”资源应用于任何系统，并且可以直接在 Niagara 资源中覆盖系统、发射器和渲染器级别的设置。这些选项允许基于可扩展性级别（例如“中等”、“高”和“史诗级”）以及平台进行控制，因此您可以区分每个级别对项目目标平台的具体含义。许多此类设置会通过剔除来减少关卡中的 Niagara 系统实例数量，但也可用于减少生成的粒子数量、禁用昂贵的渲染器，甚至完全禁用发射器和系统。 System as a Service 系统即服务

另一种减少实例数量的方法是充分利用现有系统。对于粒子特效（例如弹丸和冲击），通常会在集中区域内短时间内连续生成多个实例。虽然可以在一定程度上利用实例池来避免为这些实例重新分配组件，但重新激活它们仍然存在开销，并且依赖于之前的实例完成并返回到实例池。系统即服务 (SaaS) 方法旨在向现有系统中添加新粒子，而不是向关卡中添加新系统。5.4 版本引入了新功能来简化此工作流程，但在旧版本中可以使用用户参数。我们将在下一篇教程中更深入地介绍此策略。

## 排放源数量：降低资产层面的运营成本

构建 Niagara 系统时，尤其是在从 Cascade 架构切换过来的情况下，很自然地会为系统中的每个独特视觉元素或行为上的细微差别添加一个新的发射器。然而，由于每个发射器都会带来额外的开销，这可能会对性能产生负面冲击效果。

使用虚拟机在 CPU 上运行脚本。我们这样做主要出于两个原因：可扩展性和并行化。通过模拟 GPU 的 SIMD 特性，我们可以让所有 Niagara 脚本默认同时在 CPU 和 GPU 上运行。从一开始就将它们构建为脚本，降低了希望创建自定义脚本的用户的入门门槛，提高了可扩展性；而针对 SIMD 进行设计，则使 Niagara 能够更轻松地在 CPU 上并行执行脚本。

此虚拟机的缺点在于每个发射器都会带来额外的开销。即使粒子效果的目标是在 GPU 上进行模拟，我们仍然会在 CPU 上运行系统脚本和发射器脚本，以便它们能够与游戏线程交互。这意味着开销是固定的，避免开销的唯一方法是减少系统中的发射器数量或关卡中的实例数量。

5.4 版本中我们引入了实验性的轻量级发射器，它们牺牲了可扩展性和其他一些特性，以提升性能。在未来的版本中，由于这些发射器没有虚拟机开销，它们将成为许多用例中减少发射器数量的可行替代方案。 Mitigation Strategies 缓解策略

以下是一些可用于减少系统中发射器数量的策略。其基本思路是，将那些模拟行为基本相同、仅存在视觉元素（渲染器）或初始化数据（例如起始位置）差异的发射器进行合并。 Spawn Index 生成指数

生成索引可用于在发射器中创建具有相同行为或初始数据的粒子组。粒子会将其生成索引保存为一个参数，该参数可用于在 Niagara 脚本中动态选择不同的数据。一个常见的例子是创建粒子组，用于采样网格的不同部分，否则这些部分将具有相同的行为。例如，《堡垒之夜》中的凝结尾迹会采样角色的手和脚。在 Cascade 中，每个凝结尾迹都需要创建一个发射器，但在 Niagara 中，只需创建一个发射器即可实现整个效果，并创建四个生成组，每个生成组用于采样角色骨骼上的不同骨骼或关节。 Multiple Renderers 多渲染器

使用 Niagara，单个发射器可以拥有多个渲染器，因此可以从发射器模拟的每个粒子创建多个视觉元素。一个常见的用例是将光照渲染器与精灵或网格渲染器结合使用，这样粒子既可以发光，又能保持其几何形状。这还可以用于通过在不同的网格或精灵表示之间随机选择来改变几何形状。此外，还可以利用此功能根据距离在网格和精灵之间进行过渡。您可以将不同的参数绑定到不同的渲染器，从而允许在模拟中进行细微的变化。例如，您可以为每个渲染器绑定不同的位置，使一个渲染器产生偏移，但仍然使其跟随另一个渲染器。 Mesh renderers allow for an array of meshes to be specified,

网格渲染器允许指定一个网格数组，并通过网格索引绑定来控制渲染数组中的哪个网格。这可以替代多个渲染器，从而实现更多样化的网格形状，而无需复制渲染器，也无需设置它们的启用和禁用。可见性标签和网格数组都会带来一定的性能开销。总体而言，它们应该优于添加另一个发射器，但在选择多个发射器还是这些策略时，您的项目可能会有不同的性能表现。如果您的项目需要进一步优化，建议您比较这两种方案。

## 内存池：内存管理和减少分配

函数库允许在通过“在位置生成系统”和“附加生成系统”生成系统时选择组件池方法。启用组件池后，基于同一资源的 Niagara 组件不会像通常那样进行分配和垃圾回收。取而代之的是，系统会维护一个组件池，用于存放已分配但不再使用的组件，并在生成使用同一资源的新组件时重用这些组件。这样可以避免频繁使用的组件的分配和垃圾回收开销。 Niagara systems have control over their pool sizes and priming in the System properties under performance. Priming the pool can reduce runtime allocations,

系统允许用户在“系统属性”的“性能”设置中控制内存池大小和预加载。预加载内存池可以减少运行时内存分配，但如果资源是动态加载的，则可能会导致系统卡顿。

## 与 CPU

如前文“发射器数量开销”部分所述，所有 Niagara 模拟都会消耗 CPU 资源。选择 CPU 模拟还是 GPU 模拟只会改变粒子模拟的目标，也就是说，只有粒子生成、粒子更新和模拟阶段中的脚本会根据为发射器选择的模拟目标而改变。

粒子脚本具有最大的并行化潜力，因此它们最能受益于 GPU 优化。在大多数情况下，GPU 模拟性能更高，并且能够处理更多粒子。对于粒子数量较少的发射器，CPU 模拟可能更合适，因为 GPU 资源无法像 CPU 那样精细地分配。具体的资源分配取决于硬件配置，但模拟 1 个粒子可能与模拟 64 个粒子占用相同的资源。 It’s also important to note that in some projects, and on some platforms the GPU is the bottleneck,

值得注意的是，在某些项目和平台上，GPU 会成为性能瓶颈，此时 CPU 模拟可能更合适。这种情况在 GPU 内存较小的平台（例如移动设备）上尤为常见。反之亦然，即使是 CPU 瓶颈的项目，也可以通过将模拟（即使是粒子数量较少的模拟）转移到 GPU 上来获益。这正是为什么在项目开发过程中验证这些性能假设至关重要的原因之一。

## 其他最佳实践

对项目进行性能分析可以提供最具体的数据，帮助您了解项目的瓶颈所在，也是查找性能问题的最佳方法。但最佳实践对于避免内容创作过程中常见的或容易被忽略的错误大有裨益。这些最佳实践是 Epic Games 的特效艺术家们在参与《堡垒之夜》等项目时总结出来的，代表了我们团队内部的通用建议。当然，这些建议也有例外情况，最终需要根据具体项目来决定在哪些方面牺牲性能以换取功能和视觉效果。 Fixed vs Dynamic Bounds 固定边界与动态边界 Generally speaking,

一般来说，固定边界比动态边界性能更高，因为它所需的计算量更少。但也有例外，例如，一些特效体积相对较小但传播距离很远，就像子弹轨迹横跨大型关卡一样。它的固定边界会比实际视觉范围大得多，但大多数时候特效都会超出视野范围，不过由于其边界的存在，它仍然可能发挥作用。

## 大量粒子爆发

如果需要生成大量粒子，在同一帧内全部生成可能会导致卡顿。将生成过程分散到多个帧中可以分散计算量，从而避免卡顿。 Current Frame Data 当前帧数据

对于不依赖最新游戏数据的粒子系统，禁用“需要当前帧数据”选项可以让 Niagara 尽早开始帧内运算，从而延长运算时间。对于不移动或不采样移动物体的粒子系统，通常可以禁用此选项，但即使是一些移动的粒子也可以采样上一帧的数据，并且看起来仍然不错。尝试禁用此标志并观察是否有明显变化会很有帮助。

将复杂操作上移至堆栈顶部 Complex work that's the same for each particle or emitter,

对于每个粒子或发射器来说都相同的复杂工作，通常可以将其上移到堆栈顶部，从而减少重复工作。此外，在发射器和系统脚本中读取数据可以提高与数据接口和 Niagara 参数集合的交互性能。即使模块的全部工作范围因粒子而异，采样部分通常也可以分离出来，这仍然可以带来性能提升。 Data Interfaces 数据接口 Similar to complex work,

与复杂操作类似，发射器和粒子中重复的数据接口会占用不必要的内存。如果能将数据接口移到堆栈的更高层级，性能应该会更好。

使用属性读取器数据接口的粒子读取通常比事件读取性能更高，并且通常可以实现相同的行为。 Sorting 排序 Sorting is disabled by default, but when enabled sort tasks default to running on the GPU, and will add overhead to the GPU,

排序功能默认处于禁用状态，但启用后，排序任务默认在 GPU 上运行，这会增加 GPU 的开销，并占用索引缓冲区中的额外内存。这可能会导致绘制性能下降。
